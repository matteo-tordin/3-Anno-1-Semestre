## Race condition

Esistono situazioni (generalmente asincrone) che necessitano di più task che gestiscano le varie funzioni.

Tali task (thread) necessitano di un modo di comunicare. Si potrebbe pensare che la **memoria condivisa** sia sufficiente per risolvere questo problema.
In realtà, questa non garantisce la **consistenza**. Diversi task potrebbero star lavorando nella stessa area della memoria comune.
Questa sitauzione di definisce **race condition**.

*Vedi esempio alla [[Lecture 4 - Models of Parallel Processing.pdf#page=3|slide 3]].*

E' necessario individuare alcune **sezioni critiche** (ovvero indivisibili) per i task.
Tali sezioni devono essere eseguite in modo continuo e **garantendo la mutua esclusione**.


## Lock

L'implementazione più naive consiste nel **lock**.
* All'entrata della sezione critica, il task prende possesso del lock.
* All'uscita, lo restituisce.
* Un task che vuole prendere un lock occupato è costretto ad aspettare.


## Istruzioni atomiche

I processori moderni prevedono anche l'esistenza di **istruzioni atomiche**, che non possono essere fisicamente interrotte.
Questo può essere utile per implementare lock tramite l'istruzione **test_and_set**.

*Vedi esempio alla [[Lecture 4 - Models of Parallel Processing.pdf#page=7|slide 7]].*


## Algoritmo di Peterson

Una soluzione che garantisca non solo la mutua esclusione, ma anche la fairness è l'**algoritmo di Peterson**.

Questo è il codice per 2 task (dunque pid = 0 oppure 1):
```
//Global Variables
int flag[2] = {0, 0};
int turn=0;

//Enter critical section 
void entry(int pid) { 
	int other = 1-pid; 
	flag[pid] = 1; 
	turn = pid;
	while(flag[other] == 1 && turn == pid); 
}

//Exit critical section 
void exit(int pid) { 
	flag[pid] = 0; 
}
```

*La versione per N task è visibile alla [[Lecture 4 - Models of Parallel Processing.pdf#page=9|slide 9]].*

Tutte le soluzioni viste fino ad ora hanno il problema del **busy waiting**: si sprecano cicli di processore per l'attesa (**polling**).
Il polling può anche causare **deadlock** in sistemi a priorità fissa.

E' necessaria una soluzione che implementi l'**attesa passiva (passive waiting)**.


## Semafori

I semafori sono particolari oggetti del sistema operativo composti da due elementi
* Un **numero intero** non negativo.
* Una **coda di processi** in passive waiting sul semaforo.

Si eseguono sul semaforo due **operazioni**:
* **P(sem)**: Controlla il valore dell'intero. Se è maggiore di zero, lo decrementa di uno (in modo atomico). Altrimenti, mette il processo nella coda d'attesa e lo fa entrare in stato waiting, bloccandone l'esecuzione.
* **V(sem)**: Controlla la coda dei processi in coda. Se è vuota, aumenta di uno l'intero (in modo atomico). Altrimenti, sceglie uno dei processi in coda e lo rende disponibile all'esecuzione facendolo entrare in stato ready.

Esempio produttore-consumatore con semafori:

```
#define N 8 int buf[N]; 
int in=0, out=0; 
sem_t mutex=1;
sem_t empty=N; 
sem_t full=0;

void prod(int d){
	P(empty);
	P(mutex);
	
	buf[in] = d;
	in = (in+1) % N;
	
	V(mutex);
	V(full);
}

int cons(void) { 
	int c; 
	
	P(full); 
	P(mutex); 
	
	c = buf[out]; 
	out = (out+1) % N; 
	
	V(mutex); 
	V(empty); 
	
	return c; 
} 
```

In **Linux**, esistono due categorie di semafori:
* **Named**: pensato per la IPC (Inter-Process communication). Più processi possono fare riferimento ad un semaforo comune usando lo stesso nome.
* **Unnamed**: pensato per la comunicazione tra threads dello stesso processo. La variabile del semaforo può essere condivisa, per cui basta usare il puntatore al semaforo tra i vari thread.

I semafori named vanno **aperti** fornendo un nome e un valore iniziale.
I semafori unnamed si **inizializzano** fornendo il puntatore alla struttura e il valore iniziale.

L'operazione **V(sem)** si realizza tramite `int sem_post(sem_t *sem)`.
L'operazione **P(sem)** si realizza tramite `int sem_wait(sem_t *sem)`

Altre operazioni:
* `int sem_timedwait(sem_t *restrict sem, const struct timespec *restrict abs_timeout)` Utile per gestire un'attesa limitata ad un determinato intervallo di tempo.
* `int sem_trywait(sem_t *sem)` Utile per tentare un'attesa senza bloccare il processo (non viene messo in attesa se il semaforo ha valore 0, ma ritorna un valore di errore).


## Monitor

I **monitor** sono oggetti che **contengono**:
* dei **dati in condivisi**
* un set di **metodi** per operare su tali dati

Garantiscono inoltre le seguenti **proprietà**:
* I **dati condivisi non sono accessibili dall'esterno** del monitor ma solo attraverso i suoi metodi.
* L'invocazione dei metodi del monitor prevede la **mutua esclusione**. Un solo task alla volta può eseguire un metodo del monitor.

Si implementa la sincronizzazione nei monitor attraverso le **variabili di condizione**.
Tali variabili sono accessibili solamente tramite il monitor (e non dall'esterno). Sono quindi protette esattamente come i dati condivisi.
Si eseguono su queste variabili due metodi:
* **wait(c)**: Blocca il task e libera il monitor in una sola azione atomica.
* **signal(c)**: Sveglia uno dei processi bloccati su c. Non ha alcun effetto se non ci sono processi in attesa su c.

Analizziamo il problema produttore-consumatore tramite monitor:

```
#define N 8 

monitor ProducersConsumers {
	int buf[N]; 
	int in = 0, out = 0; 
	condition full, empty; 
	int count = 0; 
	
	void produce (int v) { 
		if(count == N) wait( empty );
		 
		buf[in] = v;
		in = (in + 1) % N; 
		count = count + 1; 
		
		if(count == 1) signal (full ); 
	}

	int consume (void) { 
		int v; 
		
		if(count == 0) wait(full );
		
		v = buf[out]; 
		out = (out + 1) % N; 
		count = count - 1; 
		
		if(count == N -1) signal (empty ); 
		
		return v; 
	} 
}
```

## Messaggi

La comunicazione tramite messaggio può essere fondamentale in sistemi in cui non esiste memoria comune tra due task (che possono essere su macchine diverse).

Questa forma di comunicazione ha bisogno di due primitive:
* Un modo per **inviare** un messaggio ad un determinato processo.
* Un modo per **bloccare il processo e attendere la ricezione** di un messaggio.

#### TIpi di comunicazione tramite messaggi

La comunicazione tramite messaggio può essere
* **Diretta:** quando un mittente invia un messaggio ad un preciso destinatario, identificandosi. A questo punto si forma un canale di comunicazione tra i due e i loro ruoli possono scambiarsi (es. comunicazione tramite IP).
* **Indirettta:** quando un mittente invia un messaggio a uno o più destinatari, dei quali non conosce l'identità. I ruoli in questo caso non possono essere scambiati, la comunicazione non è simmetrica.

Ci sono diversi metodi di sincronizzazione dei messaggi:
* **Asincrona:** Il destinatario usa una funzione di callback da chiamare in modo asincrono all'invio del messaggio. La chiamata a send() ritorna immediatamente.
* **Randezvous:** Il mittente attende la ricezione del messaggio da parte del destinatario. Si implementa di solito tramite l'invio da parte del destinatario di un messaggio di acknowledgement.
* **Request-reply**: Il mittente invia una richiesta e attende la risposta. Il destinatario elabora la risposta, bloccandosi a sua volta in attesa di una nuova richiesta.

#### Message buffering

Molto spesso la funzione send() ritorna prima che il messaggio sia stato effettivamente ricevuto.
Questo comporta (se stiamo scambiando messaggi nello stesso computer) l'uso della memoria per salvare il contenuto del messaggio.
Quando invece il messaggio si muove tra più dispositivi (es. un pacchetto nella rete), viene smistato da diversi router prima di giungere a destinazione.

**Vantaggi**: 
* Avere un buffer tra mittente e destinatario separa i due processi e rende possibile l'esecuzione concorrente di entrambi, senza attese reciproche.

**Svantaggi**:
* L'uso di un buffer rende maggiore e imprevedibile il delay tra invio e consegna del messaggio.
* Lo spazio necessario per il buffer non è regolare, e potrebbe essere potenzialmente illimitato (in casi in cui la produzione di messaggi sia più rapida della ricezione).
